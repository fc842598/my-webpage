# 天纪元堂泛化排查结论
整理时间：2026-04-03

目的：

- 回答“那 5 条不一致到底是什么意思”
- 区分“样本失败”和“规则失败”
- 收束出下一步该怎么做，避免继续按样本加特例

---

## 1. 先说结论

那 `5` 条“不一致”，不是“这 5 条样本没用”，也不是“反推失败”。

它真正表示的是：

- `天纪.exe` 给出的 `先天卦 -> 后天卦` 真值是稳定的
- 当前仓库 `getYuanTangDetail(...)` 的“泛化元堂规则”不够对
- 也就是：现在坏掉的是“总规则”，不是那 5 条样本本身

换句话说：

- 这 5 条是很有价值的反例
- 它们不是要你去给每条写特例
- 而是逼着我们把“元堂总规则”改对

## 3. 这 24 条到底说明了什么

### 3.1 当前仓库规则不是“全错”

当前 [generator.js](C:/Users/1/Desktop/家里用的图标/src/ziping/generator.js) 的 `getYuanTangDetail(...)`，放到这 `24` 条真值上：

- `19 / 24` 命中
- `5 / 24` 不命中

这说明：

- 现有实现不是完全胡算
- 但它不是可泛化的稳定规则
- 所以不能拿“7 条老样本都过了”来证明它已经对

### 3.2 那 5 条不一致有明显共性

这 `5` 条反例里，有 `4` 条都落在：

- `upper-six / non-zi`
- 且真元堂都在 `阳爻池`

而当前实现恰好把它们都导向了 `阴爻池`。

剩下 `1` 条是：

- `female / lower-six / 水雷屯`
- 真元堂也在 `阳爻池`

这说明当前实现最值得优先怀疑的，不是“池内轮转顺序”，而是：

- `到底先选阳池还是阴池`

### 3.3 这 5 条不是“顺序错了”，而是“池子选错了”

这点很重要。

对这 `5` 条样本来说，只要把“选池”改对，按现有的：

- 时组六时顺序
- 在池中按自然爻序轮转
- 位置对池长度取模

就能直接落到正确元堂。

也就是说：

- 当前大头问题不是“池内排法”
- 而是“阳池 / 阴池分流规则”

## 4. 一个更强的基线：书面规则其实比当前实现更稳

如果暂时先退回《天机道》P49 的最小书面规则：

- `上六时（子丑寅卯辰巳） -> 阳爻池`
- `下六时（午未申酉戌亥） -> 阴爻池`

并且维持现有的池内轮转顺序不变，那么这 `24` 条样本里会变成：

- `22 / 24` 命中
- 只剩 `2 / 24` 不命中

这比当前仓库规则的 `19 / 24` 明显更强。

这条结论意义很大：

- 当前实现里那套“上六时结合命阴阳、下六时固定阴池”的软件校准层，至少有一部分是校错方向了
- 《天机道》的书面基线，反而更接近 `天纪.exe` 的大面表现

   - 类型：`female / upper-six / ordinary`

   - 先天卦：`水雷屯`
   - 真元堂：`1`
   - 书面基线会落到：`2`
   - 类型：`female / lower-six / three-zizun / water-thunder-tun`

所以现在真实的状态不是“元堂规则一团黑箱”，而是：

- 大框架已经缩到 `22 / 24`
- 还差 `2` 个异常口袋没有解释完

这和“还差一整个体系没逆出来”是完全不同的量级。

## 6. 这对“至少过去 100 年都准”意味着什么

如果你的目标是：

- 不做单盘特例
- 尽量让过去 `100` 年内都能稳定排

那正确顺序应该是：

1. 先把元堂规则收敛到一个“主规则 + 极少数已证实分支”
2. 再做大范围随机抽检
3. 不是先上代码赌它会普适

当前最合理的泛化路线是：

### 第一步

把元堂主规则临时收束为：

- `upper-six -> 阳爻池`
- `lower-six -> 阴爻池`

这一版已经能解释 `24` 条中的 `22` 条。

### 第二步

围绕剩余两个口袋继续补真值，不是补随机盘：

- `female / upper-six / ordinary`
  - 尤其补 `寅 / 卯 / 辰`
  - 尤其补 `春季阳令`

- `female / lower-six / 水雷屯`
  - 尤其补 `申 / 酉 / 戌 / 亥`
  - 尤其补 `子月 / 丑月`

### 第三步

只有当这两个口袋的分支被样本坐实后，才去改 [generator.js](C:/Users/1/Desktop/家里用的图标/src/ziping/generator.js)。

这才是“往过去 100 年泛化”的方向。

---

## 7. 下一步最该做什么

下一步不该是“按这 5 条写补丁”，而应该是：

1. 把现有 `24` 条元堂真值固化成一个专用校验集
2. 再补两组定向样本：
   - `female / upper-six / ordinary`
   - `female / lower-six / 水雷屯`
3. 只要这两组一补，就可以决定：
   - 是直接采用书面基线
   - 还是在书面基线之上，再加一个很小的女性分支

然后再进入代码修改。

---

## 8. 现在能下的判断

现在已经可以明确下的判断只有这几个：

- 那 `5` 条“不一致”不是采样失败，而是当前总规则失败
- 当前元堂问题本质上是“选池规则”不够对，不是“池内顺序”黑箱
- 书面基线 `upper-six -> 阳池 / lower-six -> 阴池` 比当前实现更接近天纪本体
- 还没收束的范围，已经缩到 `2` 个女性口袋，不是整套算法都不行

所以，方向是对的，而且已经从“全黑箱”缩成了“两个剩余分支待证实”。
