# 文章双稿择优与整改机制

## 目标

逐篇比较站内原稿与外部改写稿。不是默认采用新稿，也不是默认保留旧稿；最终只采用更准确、更自然、更符合原搜索问题的版本。URL、发布日期、canonical 和既有索引关系保持不变。

## 三个角色

1. 内容评论员：审搜索意图、标题与 URL 一致性、紫微术语、判断条件、组合例子、结构和 SEO 风险。
2. 读感评论员：审真人读感、机器模板味、重复、清晰度、实用性、营销克制度及恐吓或绝对化表达。
3. 终审编辑：读取两份独立意见，选择保留原稿、保留候选稿、融合重写或整篇重写，并对成稿负责。

候选稿缺失时也不能跳过两位评论员：两人改为独立审查原稿是否可保留、需要保守精修或需要整篇重写。

## 五评论员补审

候选稿缺失或首轮结果存在争议时，升级为五评论员：SEO 搜索意图、紫微专业逻辑、英文真人读感、机器味与安全、最终仲裁。前四位逐篇独立给出 `PASS` 或 `REVISE`，任一位退回就必须重写；第五位可以追加退回，不能用多数票覆盖明确的专业错误或安全问题。

退回稿按问题归口整改，整改后重新检查标题、术语定义、宫位几何、格局成立条件、条件例子、排盘顺序、字数、重复和来源痕迹。返工人不得审核自己的修改；每篇返工稿必须再由内容/术语、读感/安全两名独立评论员复审，两人都对同一个最终正文哈希给出 `PASS`，才能补入双评论员记录和最终 QA。

首轮直接通过的稿件同样不能只记录口头结论：四名评论员都必须绑定当时看到的最终正文哈希。合并器只接受“四份首轮通过哈希完全一致”或“返工后两份独立复审哈希完全一致”这两条路径，不允许合并脚本替评论员自行签发通过。

## 硬门槛

候选稿出现以下任一问题，不得直接采用：

- H1 或正文偏离原 URL 的搜索意图。
- 擅改文章 ID、语言、URL、发布日期或修改日期。
- 紫微术语被简化成单星、单宫或单一年龄的绝对结论。
- 出现保证准确、灾难化预测、恐吓、虚构客户心声或攻击同行。
- 出现来源追踪、模型自述、提示词、行号或禁用来源名称。
- 结构过薄，缺少必要落宫条件、组合例子或排盘顺序。

## 选择规则

- 两位评论员都选候选稿、无硬门槛，且候选在两份评分中都至少高 3 分，才进入“保留候选稿”。
- 两位评论员都选原稿时保留原稿；原稿仍有禁用词或质量问题时改为整篇重写。
- 两位评论员意见不同，或一版结构好、另一版例子好时，进入融合重写。
- 两版都有明显问题时整篇重写，不为凑数量降低标准。
- 所有选择都只是暂定，终审编辑完成后才允许替换页面。
- 落盘前同时核对文章 ID、`sourceFile`、URL、canonical 和正文身份指纹；现有页面必须匹配审核时原稿或已批准终稿之一，否则中止，避免错页覆盖或覆盖评审后的人工修改。
- 卡片和 ItemList 只按精确文章 URL 更新：卡片必须通过 `.card-link` 唯一定位，JSON-LD 必须解析后只修改对应 `ListItem.name`，禁止全局字符串替换。

## 终审五遍

1. 意图审：标题、导语和结论是否真正回答原搜索问题。
2. 专业审：强弱、落宫、会照、四化与现实解释是否有条件、不过度断言。
3. 人味审：删除套话、模型腔、夸张口号、连续排比和不自然英文。
4. 查重审：与站内标题、开头、例子及表达查重，必要时换写法。
5. 技术审：正文结构、JSON-LD、hreflang、内链、feed、sitemap 及页面渲染全部通过。

## 进度状态

每篇文章固定保留：原稿、候选稿、自动风险标记、内容评论、读感评论、暂定选择、终审说明、替换状态和验证结果。没有终审记录的文章不得发布。

终审队列固定按每批 20 篇拆分。批次内每篇完成终审、替换和验证后才关闭该批次，防止长文档截断、漏稿或错位。

每次终审生成正文哈希，最终 QA 审阅前从队列读取该哈希，并把它写入 QA 结果；禁止在审阅完成后补绑哈希。正文一旦变化，旧 QA 自动失效。

页面只允许由 `scripts/apply-approved-article-rewrites.py` 更新。脚本默认演练，显式传入 `--apply` 才写文件；整批预检通过后才落盘。更新范围包括正文、可见 H1、title、description、OG 和 Article JSON-LD，同时锁定 URL、canonical、hreflang、`datePublished`、`dateModified` 与页面时间。旧正文内链、章节锚点、侧栏继续阅读和快速排盘必须保留，章节变化时只重建目录链接。
