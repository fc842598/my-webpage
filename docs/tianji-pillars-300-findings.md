这份文档只处理“天纪四柱入口”这一层，不碰先天卦、后天卦和流年推进的完整规则归纳。

## 1. 当前四柱入口比对结果

把现有 `tianji-bazi.js` 对照 300 条真值样本重算四柱，结果是：

- 总样本：`300`
- 当前入口完全命中：`280`
- 当前入口不命中：`20`

不命中的 20 条全部落在同一个口袋：

- `civilSlot = 未`

也就是说，当前天纪式四柱入口已经命中了 `280/300`，剩下的唯一系统性残留就是 `未时`。

## 2. 未时残留的具体形态

现有 `tianji-bazi.js` 对 `未` 按标准时支处理，会得到正常的未时柱；但天纪真值不是这样。

例 1：`1966-06-25 男 未时`

- 天纪真值：`丙午 甲午 乙卯 丁亥`
- 当前入口：`丙午 甲午 乙卯 癸未`

例 2：`1999-12-26 男 未时`

- 天纪真值：`己卯 丙子 壬子 辛亥`
- 当前入口：`己卯 丙子 壬子 丁未`

例 3：`2021-03-28 女 未时`

- 天纪真值：`辛丑 辛卯 乙亥 丁亥`
- 当前入口：`辛丑 辛卯 乙亥 癸未`

例 4：`1991-06-15 男 未时`

- 天纪真值：`辛未 甲午 丙辰 己亥`
- 当前入口：`辛未 甲午 丙辰 乙未`

这说明天纪在 `未时` 这一格，并不是简单按“民用 13:00-15:00 -> 未支”走标准时柱。

## 3. 300 条样本里，只有一对时段会“共用四柱”

把同一天、同一性别的样本两两对比后，当前 300 条样本里，只有一种“同四柱”现象：

- `未 ~ 亥`

统计结果：

- 同四柱配对总数：`20`
- 配对类型：全部都是 `未 ~ 亥`
- `sameXiantian`: `20/20`
- `diffHoutian`: `20/20`
- `diffLiunianLen`: `10/20`

这条结论非常硬：

1. 天纪里 `未` 和 `亥` 在这批样本上，会落到完全相同的四柱。
2. 它们随后又会分叉到不同的后天卦。
3. 其中一部分还会继续分叉到不同的流年总长度。

所以，天纪并不是“时段信息完全压缩进四柱以后就结束了”。

## 4. 关键样本：未/亥同四柱、同先天、但后链分叉

例：`1966-06-25 男`

`未`
- 四柱：`丙午 甲午 乙卯 丁亥`
- 先天卦：`山风蛊`
- 后天卦：`风火家人`
- 流年总长度：`93`

`亥`
- 四柱：`丙午 甲午 乙卯 丁亥`
- 先天卦：`山风蛊`
- 后天卦：`巽为风`
- 流年总长度：`93`

再看 `1966-06-25 女`

`未`
- 四柱：`丙午 甲午 乙卯 丁亥`
- 先天卦：`风地观`
- 后天卦：`水风井`
- 流年总长度：`87`

`亥`
- 四柱：`丙午 甲午 乙卯 丁亥`
- 先天卦：`风地观`
- 后天卦：`地水师`
- 流年总长度：`81`

这说明 `未/亥` 的差异不是四柱层，也不是先天卦层，而是四柱之后还有一层“时段状态”在继续起作用。

## 5. 现有网站结构为什么先天装不下这类差异

当前网站运行链路是：

- `tianji-bazi.js` 先把输入时间压成四柱
- `runtime.compute(pillars, gender, birthYear, maxAge)`
- `generator.generate(pillars, gender, birthYear, maxAge)`

也就是说，运行时传进生成器的只有：

- `pillars`
- `gender`
- `birthYear`
- `maxAge`

没有额外的：

- `civilSlot`
- `slotIndex`
- `timeSlotKind`

这会导致一个结构性问题：

如果两条盘在天纪里“同四柱但不同后天/流年”，现有网站生成链路就没法表达这件事，因为它在四柱之后已经失去区分这两条盘的输入信息了。

## 6. 现有生成器在未/亥同四柱时会固定落到哪一路

拿 `1966-06-25 男` 这组样本做实算：

输入四柱：`丙午 甲午 乙卯 丁亥`

天纪真值：
- `未`：`山风蛊 -> 风火家人 -> 93`
- `亥`：`山风蛊 -> 巽为风 -> 93`

当前生成器结果：
- `山风蛊 -> 巽为风 -> 93`

也就是说，当前网站在“未/亥同四柱”时，会自动落到 `亥` 那一路，`未` 这一条在现结构里没有入口可区分。

## 7. 当前阶段的结论

到这一步，可以先锁住 3 条结论：

1. 现有四柱入口已经基本接近天纪，`282/300` 命中。
2. 剩余唯一系统残留是 `未时`。
3. 天纪里存在“时段状态在四柱之后继续生效”的现象；至少 `未/亥` 这一对如此。

## 8. “原始时段进入元堂”假设的命中率

我又拿这 20 组 `未/亥` 对照做了一层反推：

- 保持天纪真值里的四柱不变
- 保持先天卦不变
- 只把“原始时段分支”送进 `getYuanTangDetail(...)`

结果如下：

- `未` 端命中：`20/20`
- `亥` 端命中：`11/20`
- 两端同时命中：`11/20`

这说明：

1. `未` 这一边已经非常像“先折成亥柱，再按原始未时段取元堂”。
2. 但 `亥` 这一边还没有被当前规则完全解释。

### 8.1 未端为什么已经基本坐实

对 20 组 `未/亥` 对照，`未` 端都能唯一反推出一个元堂爻，而且和“原始时段 = 未”送入当前元堂规则的结果完全一致。

这意味着后续真要修网站结构时，最值得优先尝试的不是改四柱公式，而是：

- 四柱层允许 `未` 折到 `亥`
- 但运行时继续保留一个独立的 `timeSlotKind` / `slotIndex`
- 元堂层按原始时段而不是按折叠后的时支继续走

### 8.2 亥端还剩 9 组未解释

剩余 `9` 组 `亥` 样本里，现象分两类：

1. `8` 组能反推到一个明确元堂爻，但这个爻位更像当前规则里的“上六时 / 阳池”分支，而不是普通 `亥` 分支。
2. `1` 组甚至在当前 `computeHouTian(...)` 体系里根本找不到对应爻位。

最突出的异常样本：

- `1991-06-15 女`
- 四柱：`辛未 甲午 丙辰 己亥`
- 先天卦：`地天泰`
- 亥端后天卦：`天山遯`

这一条在当前 `地天泰 + 午月` 的后天映射里，`line1..line6` 都推不出 `天山遯`，说明它不是单纯“换一个元堂爻”就能解释。

### 8.3 其余 8 组亥端更像哪一类时段

其余 8 组未解释的 `亥` 端，反推出来的目标元堂爻，更像当前规则里这些分支：

- `子` 固定阳池
- 或 `丑 / 寅 / 卯 / 辰 / 巳` 这类上六时阳池分支

也就是说，天纪在这部分 `亥` 样本上，很可能还有第二层隐藏状态：

- 不是简单的 “原始时段 = 亥”
- 也不是 “四柱里的时支 = 亥”
- 而是某种会把后链切到阳池/上六时逻辑的内部状态

## 9. 下一步最合理的拆法

下一步不应该立刻改网站代码，而应该继续反推这两层：

1. 天纪为什么把 `未` 输入折叠成 `亥` 四柱。
2. 即使四柱相同，天纪又是通过什么隐藏状态把 `未` 和 `亥` 分开推进到不同的后天卦和流年序列。
3. 对那 `9` 组未解释的 `亥` 样本，再继续判断它们到底是：
   - 特殊元堂选池
   - 特殊后天卦映射
   - 还是更早一层的时段组别切换

最直接的后续工作：

1. 把 20 组 `未/亥` 样本按：
   - 性别
   - 月令
   - 先天卦
   - 后天卦
   - 流年总长度
   重新分组。
2. 看 `未` 相对 `亥` 的分叉，究竟更像：
   - 元堂规则分叉
   - 后天卦映射分叉
   - 还是更早一层的“时段组别”分叉。
3. 先单独攻那 `9` 组未解释的 `亥` 样本，判断它们是否能被：
   - 阳池/上六时假设
   - 特殊后天映射
   - 三至尊或口袋规则
   解释。
4. 然后再决定网站应该补的是：
   - `timeSlotKind`
   - `slotIndex`
   - 还是一个更明确的“天纪输入时段状态”字段。
