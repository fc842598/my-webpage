# 天纪元堂规则清单
整理时间：2026-04-03

目的：
- 只收束“元堂怎么定位”
- 把《天机道》书面规则、当前仓库实现、`天纪.exe` 样本校准分开
- 给后续修“后天卦”提供前置判断，不再把问题一股脑归到 `computeHouTian()`

---

## 1. 先说结论

这一步最重要的结论有三条：

- 如果 `先天卦` 已经对，但 `后天卦` 大量不对，第一嫌疑应该是 `元堂`，不是后天卦公式。
- 《天机道》已经明确给了元堂的“起时法”主框架，但没有把所有软件边界条件都写成一句话。
- `天纪.exe` 当前已知样本显示，软件在 `子时` 和部分“命阴阳 / 时组”边界上，确实可能还有书面页之外的额外分支。

换句话说：

- “元堂完全没规则”这个判断不成立。
- “只靠一句‘阳时取阳爻、阴时取阴爻’就能完全复刻 EXE”也不成立。

---

## 2. 《天机道》已经明写的元堂规则

最关键的书面入口在《天机道》P49：

- `凡阳时生人，则取本卦阳爻。从子时数起。`
- `阴时生人，则取本卦阴爻。从午时数起。`

来源：
- [《天机道》PDF](https://www.vr-d.com/pdf-file/%E5%A4%A9%E6%9C%BA%E9%81%93-%E5%80%AA%E6%B5%B7%E5%8E%A6%E7%AE%80%E4%BD%93-%E5%80%AA%E6%B5%B7%E5%8E%A6.pdf)

这两句至少把元堂框架定死了：

1. 先把先天卦拆成 6 爻。
2. 按出生时属于 `阳时` 还是 `阴时` 分流。
3. `阳时` 走本卦阳爻池，起点是 `子时`。
4. `阴时` 走本卦阴爻池，起点是 `午时`。
5. 随时序轮转，落到当前元堂爻。

这一步还没有涉及后天卦和流年卦，它只回答“元堂从哪里来”。

## 3. 书里图式进一步透露的东西

《天机道》P50-P51 不是只写一句口诀，而是把元堂拆成整页图式：

- `壹、阳爻起时法`
- `贰、阴爻起时法`
- 分别列出 `一阳爻 / 二阳爻 / 三阳爻 / 四阳爻 / 五阳爻 / 六阳爻`
- 以及 `一阴爻 / 二阴爻 / 三阴爻 / 四阴爻 / 五阴爻 / 六阴爻`

来源：
- [《天机道》PDF](https://www.vr-d.com/pdf-file/%E5%A4%A9%E6%9C%BA%E9%81%93-%E5%80%AA%E6%B5%B7%E5%8E%A6%E7%AE%80%E4%BD%93-%E5%80%AA%E6%B5%B7%E5%8E%A6.pdf)

这说明两件事：

- 元堂不是简单查一张“时支 -> 固定爻位”的表，而是要先看“目标池里有几条可用爻”。
- 同一组六时，是在“目标池”里循环落位，不是直接在 1-6 爻里机械顺推。

从这些图式能收束出一个最低一致解释：

1. 先挑出“本卦中同性质的爻位”形成候选池。
2. 候选池按卦中自然爻序参与轮转。
3. 时序按：
   - `阳时 = 子丑寅卯辰巳`
   - `阴时 = 午未申酉戌亥`
4. 若目标池数量少于 6，则按轮转位置对池长度取模。

这也是当前仓库 `getYuanTangDetail(...)` 的主体思路来源之一：

## 4. 书面材料为什么还不足以直接复刻 `天纪.exe`

问题不在于书里完全没讲元堂，而在于它讲了“主框架”，但图式里还露出了更多维度。

### 4.1 六阳爻 / 六阴爻图式已经出现额外分组

P50-P51 的 `六阳爻元堂卦例`、`六阴爻元堂卦例` 下面，书里又继续按这些条件分组：

- `男命阳时生人`
- `男命阴时生人`
- `女命阳时生人`
- `女命阴时生人`
- 还分 `冬至后夏至前生人`
- 与 `夏至后冬至前生人`

这说明：

- “阳时取阳爻 / 阴时取阴爻”只是主框架。
- 真正的 `时支 -> 元堂爻` 图式，至少在某些边界盘里，还会受 `命阴阳`、`阴令 / 阳令` 影响。

所以，如果只把书面口诀压缩成：

- `上六时 -> 阳爻池`
- `下六时 -> 阴爻池`

那很可能会丢掉 `天纪.exe` 里真正使用的细分图式。

### 4.2 书里没有把“软件特例”整理成程序化总表

书里是按卦例和图式讲法展开的，不是按“完整程序接口文档”写的。  
因此，下面这些问题，单靠当前公开页还不能完全定死：

- `子时` 是否和其他阳时完全同规则
- `早子 / 夜子` 是否同一处理
- `命阴阳` 进入元堂分支的精确位置
- `阴令 / 阳令` 到底影响所有盘，还是只影响书里那些特殊图式

这也是为什么“看过课程框架”还不等于“已经拿到 EXE 级算法”。

## 5. 当前仓库与 `天纪.exe` 样本给出的软件层信息

这部分不是《天机道》明文，而是当前项目已经用 `天纪.exe` 样本反推出来的东西。

可参考：

- [tianji-ziping-step3-complete-chain.md](C:/Users/1/Desktop/家里用的图标/docs/tianji-ziping-step3-complete-chain.md)

- [ziping-golden-cases.js](C:/Users/1/Desktop/家里用的图标/fixtures/ziping-golden-cases.js)

当前仓库里，元堂实现已经叠了这层样本校准：

- 上六时（`子丑寅卯辰巳`）：
  - 倾向按 `命阴阳` 选池
- 下六时（`午未申酉戌亥`）：
  - 倾向走阴爻池
- `子时`：
  - 当前实现按 `天纪.exe` 样本，单独作为特例处理
  - `早子 / 夜子` 都固定走阳爻池

这个“子时固定阳爻池”的结论，不是直接抄自书面口诀，而是为了对齐 EXE 样本加出来的。

因此，这一层要这样看：

- 它是“软件校准假说”
- 不是“已经被《天机道》全文明写死的标准规则”

## 6. 目前最稳的实现分层

如果下一步只想把元堂修准，而不是继续一起碰后天卦和年卦，最稳的写法应该分成两层：

### 6.1 书面基线层

只实现《天机道》已经能确定的部分：

```text
输入：
  先天卦六爻
  hourBranch

1. 如果 hourBranch 属于 子丑寅卯辰巳：
   - 目标池 = 本卦阳爻
   - 起时序 = 子丑寅卯辰巳
2. 如果 hourBranch 属于 午未申酉戌亥：
   - 目标池 = 本卦阴爻
   - 起时序 = 午未申酉戌亥
3. 在目标池中按时序轮转定位元堂
```

这一层只代表“书面最小共识”。

### 6.2 EXE 校准层

只在样本已经明确证明时，单独叠加：

- `子时` 特例
- `命阴阳` 影响选池
- 其他经样本明确验证的边界条件

这样做的好处是：

- 你可以清楚知道，某条规则到底是“书里定的”还是“软件补的”。
- 后面一旦新样本推翻某个特例，只改校准层，不会把书面主框架也一起打烂。

## 7. 现阶段已经能当作“高可信”的元堂规则

高可信：

- 元堂必须先于后天卦。
- 阳时 / 阴时两套起时法真实存在。
- 阳时起点是 `子时`，阴时起点是 `午时`。
- 元堂是在“目标性质爻池”里轮转，不是直接在 1-6 爻硬排。
- `早子 / 夜子` 需要单独检查，不能草率按普通时辰处理。

中可信：

- 当前仓库“上六时结合命阴阳、下六时偏阴爻池”的实现，和现有一小批 EXE 样本并不冲突。

低可信 / 仍待补样本：

- 这套当前实现是否足以覆盖多数新盘。
- `命阴阳` 与 `阴令 / 阳令` 进入元堂分支的完整边界。
- 六阳爻 / 六阴爻图式在程序里应如何统一抽象。

## 8. 这份文档对当前项目的直接意义

它解决的不是“元堂已经完全逆完”，而是把排查顺序收紧成了下面这样：

1. 先确认 `四柱 -> 先天卦` 是否对。
2. 再确认当前盘落在哪个元堂分支：
   - 书面基线分支
   - 还是 EXE 校准特例分支
3. 只要 `元堂Line` 一错，先天卦再对，后天卦也会整体歪掉。
4. 所以后天卦修不准时，先审 `yuanTangLine`，不要先怀疑 `computeHouTian()`。

---

## 9. 下一步最值得做什么

最值的不是继续猜年卦，而是补一批“只测元堂”的真值样本。

建议样本矩阵至少覆盖：

- 男 / 女
- 阳命 / 阴命
- 早子 / 夜子
- 上六时非子时
- 下六时
- 六阳爻卦
- 六阴爻卦
- 三至尊卦与普通卦
- 冬至后夏至前
- 夏至后冬至前

然后每条样本只抓四个字段：

- 四柱
- 先天卦
- 元堂爻
- 后天卦

这样才能把“元堂错了”从“后天卦错了”里彻底拆开。
